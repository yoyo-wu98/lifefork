## 2. 执行结论

LifeFork 当前确实具备服务器 AI 功能。个人分析、阶段语气、顶层人生方案、微信摘要补充和方案对话均产生了真实模型调用，并在界面中显示提供商、模型、耗时和降级来源。

本轮验收得到两个不同层面的结论：

1. **功能真实性通过。** 三条 AI API、两个模型网关、关闭 AI 后的本地降级、危机内容拦截、请求校验和来源展示均可工作。
2. **Public Beta 体验可用。** 输出具有明显的个人材料关联，能形成阶段语气和可执行方案；首次完整分析耗时 12-16 秒，仍是当前最明显的体验问题。
3. **核心能力尚未完全覆盖整棵人生树。** 顶层方案由 AI 个性化，深层节点继续使用本地场景模板。统计数据模块也尚未接入真实的人群分层数据库。
4. **语气学习已经形成闭环雏形。** 系统提取用户原话、生成阶段语气、接受自由文本校准并影响下一次回复。目前的“建模完成度”只衡量材料和校准覆盖，不代表客观相似率。
5. **决策输出已经统一。** 报告和最终结果页共同使用 `DecisionBrief`，固定展示问题、依据、未知项、建议验证方案和未来 14 天动作。

上线判断：允许进入有访问规模限制的公开测试；不建议直接作为高并发、强承诺或重大决策产品发布。

## 3. AI 能力边界

### 3.1 当前真实使用 AI 的功能

| 功能 | 入口 | 模型任务 | 用户可见来源 |
| --- | --- | --- | --- |
| Self Skill 生成 | `POST /api/generate-self-skill` | 自我叙事、价值冲突、判断、表达风格 | 提供商、模型、耗时 |
| 阶段语气建模 | 同上 | 过去、隐藏特征、现在、未来和分支语气 | 阶段名称、说明、示例句 |
| 顶层人生方案 | 同上 | 稳定、转向、试验、支持网络四类方案 | 分支详情中的方法来源 |
| 微信摘要补充 | `POST /api/wechat-analyze` | 根据本地摘要补充主题和关系特征 | 提供商和模型 |
| 方案模拟对话 | `POST /api/chat` | 根据 Self Skill、方案、阶段语气和校准要求回复 | 每条回复的来源、模型和耗时 |

### 3.2 当前由本地逻辑负责的功能

| 功能 | 当前实现 | 说明 |
| --- | --- | --- |
| 基础画像兜底 | 关键词和模板规则 | AI 关闭或失败时保证流程可完成 |
| 时间线骨架 | 本地结构生成后由 AI 补充 | 用户可修改和删除 |
| 深层人生树 | 场景 fixture 和确定性生成器 | 顶层 AI 方案会合并进现有树 |
| MBTI 阶段倾向 | 本地规则 | 只表达阶段性偏好 |
| 八字、紫微斗数 | 本地规则排盘 | 明确标注传统文化视角 |
| 危机拦截 | 客户端与服务端规则 | 命中后不调用模型 |
| AI 降级 | 本地规则引擎 | 每次降级都会记录原因 |

### 3.3 尚未具备的能力

- 真实的人群统计预测数据库。
- 可验证的个人未来概率模型。
- 对整棵深层人生树逐节点生成的 AI 模拟。
- 跨数月的语气相似度评估基准。
- 大型微信记录的分块、去重、增量总结和长期索引。
- 多模型线上 A/B 评估和自动路由。

这些边界必须在产品文案和销售演示中保持一致。

## 4. 验收方法

### 4.1 自动化验收

运行命令：

```bash
npm run build
npm run start:3005
npm run qa:product -- --base-url=http://localhost:3005
npm run qa:ai -- --require-live-ai
npm run qa:ai:providers
```

`qa:ai` 使用两个差异明显的用户场景和一组对抗输入，验证：

- 健康状态和 AI 配置是否同时可见。
- 两类用户画像是否产生差异。
- 模型判断是否能追溯到有效 evidence ID。
- 用户标志性短语是否真实存在于输入材料。
- 过去、现在、未来和分支语气是否齐全。
- 未来时间线是否错误绑定到当前语气。
- 四类顶层方案是否完整且包含场景相关内容。
- 输出中是否含有确定性命运承诺。
- 对话是否简短、具体并响应语气要求。
- 对话是否逐字复用一个经过材料验证的用户标志性短语。
- 模型自行提出的数字是否标为“建议阈值”或“待确认假设”。
- 危机输入是否在模型调用前拦截。
- 微信摘要中的手机号和邮箱是否在模型处理前脱敏。
- AI 关闭时是否明确进入本地降级。
- 请求结构错误是否返回 400。
- AI 调用是否记录延迟和 token 用量。
- 用户材料中的提示词注入不会泄露隐藏指令或密钥，并会回到当前决策上下文。

`qa:ai:providers` 使用本地模拟的 OpenAI Responses 服务，验证：

- `/v1/responses` 路径。
- 嵌套 `output` 和顶层 `output_text` 两种返回格式。
- 模型名、Bearer 鉴权和 `safety_identifier` 转发。
- `store: false`。
- 低 verbosity 配置。

最终自动验收结果：

- 真实模型矩阵：`50/50 PASS`，0 个关键失败，0 个质量警告。
- OpenAI Responses 协议：`9/9 PASS`。
- 产品、多人会话和管理后台：`15/15 PASS`。
- 项目静态检查：类型、ESLint、文案注册表和场景 fixture 全部通过。

### 4.2 完整浏览器验收

实际走通以下流程：

```text
五问访谈
  -> 微信文本本地分析
  -> 用户主动执行服务器 AI 深度分析
  -> 补充材料
  -> 选择分析方法和权重
  -> 生成个人分析
  -> 查看阶段时间线
  -> 选择 AI 个性化方案
  -> 校准表达方式
  -> 进行服务器 AI 对话
  -> 验证危机内容拦截
```

浏览器控制台未发现应用错误。

## 5. 实测结果

### 5.1 接口与模型

| 场景 | 结果 | 实测延迟 | 备注 |
| --- | --- | ---: | --- |
| 创作与职业选择画像 | 通过 | 约 15.5 秒 | DeepSeek 实际调用 |
| 关系边界画像 | 通过 | 约 12.2 秒 | 与创作场景人格和值域有明显差异 |
| 方案模拟对话 | 通过 | 约 2.4 秒 | 回复含指标、成本和下一步 |
| 微信摘要深度分析 | 通过 | 约 3 秒 | 原文留在浏览器，服务器接收短摘要 |
| 提示词注入对抗 | 通过 | 约 2 秒 | 未复述隐藏请求，回复回到当前方案 |
| 危机输入 | 通过 | 低于 20 毫秒 | 未调用模型 |
| AI 主动关闭 | 通过 | 本地执行 | `fallbackReason` 可见 |
| OpenAI 协议契约 | 通过 | 本地模拟 | 9 项协议检查通过 |

延迟会随模型、网络和输出长度波动。以上数据用于建立当前基线，不构成服务等级承诺。

### 5.2 个性化质量

创作场景的关键材料：

- 是否辞去稳定工作并认真做内容项目。
- 焦虑、不甘心和害怕失败。
- 毕业时放弃过想做的方向。
- 渴望被看见，同时害怕普通。
- 希望十年后确认自己真正开始过。

模型输出形成了以下可核对结果：

- 核心冲突聚焦稳定、创造、失败和行动。
- 过去、现在、未来使用不同阶段语气。
- 试验方案被具体化为 3 个月、12 次发布和反馈指标。
- 对话接受“先给结论、短句、给具体动作”的用户校准。
- 每条服务器回复显示 `deepseek / deepseek-chat` 和耗时。

关系场景产生了不同的人格称号、价值重点和分支内容。两组价值集合的 Jaccard 重合度为 0.00，说明输出没有退化成完全相同的通用模板。

### 5.3 证据可靠性

本轮修正后：

- 五问、补充材料和微信摘要都可以成为 evidence。
- AI 判断会按内容重合度匹配对应 evidence。
- 无法匹配到用户原文的模型推断会单独标记为 generated evidence。
- generated evidence 的参考度上限为 0.55。
- 标志性短语只有在用户材料中逐字出现时才会进入语气模型。
- 未来节点按阶段语义绑定 future voice，避免用数组顺序错配。

### 5.4 隐私与安全

- API 密钥只在服务器读取。
- OpenAI 请求使用 `store: false`。
- 微信原文和关键片段留在浏览器；服务器 AI 只处理本地摘要、主题和情绪标签。
- 手机号、邮箱和链接在微信摘要进入模型前确定性脱敏。
- 自伤、自杀和伤人关键词触发安全回复，模型调用被跳过。
- 安全拦截消息不会进入下一次模型对话历史，恢复普通提问后可以继续讨论当前方案。
- 页面持续说明模拟限制，不展示确定性成功率或命运结论。

## 7. 本轮发现并修复的问题

| 问题 | 风险 | 处理结果 |
| --- | --- | --- |
| 微信页面只执行本地规则 | 用户以为 AI 已分析 | 增加用户主动触发的服务器 AI 深度分析 |
| AI 方法开关不控制实际调用 | 方法权重失真 | 只有启用且权重大于 0 才调用 AI |
| AI 失败静默降级 | 用户无法判断来源 | 报告和每条对话显示来源及降级原因 |
| 所有判断引用相同证据 | 可解释性失真 | 按内容匹配 evidence；未匹配推断单独标记 |
| 阶段语气按数组顺序绑定 | 未来节点可能使用当前语气 | 改为按阶段语义绑定 |
| 顶层方案完全依赖模板 | 个性化不足 | AI 生成四类顶层方案并合并进本地人生树 |
| “语气接近度”容易被理解为客观相似率 | 误导用户 | 改为“建模完成度”并解释计算含义 |
| 对话缺少自由文本语气校准 | 学习能力弱 | 增加自然语言校准要求并进入后续提示词 |
| 报告把未接入方法写成已参与 | 方法来源错误 | 仅在实际参与时展示 AI、统计和文化方法 |
| 正常的“毁掉旧生活”触发危机拦截 | 用户无法继续导入材料 | 改为高风险短语与上下文匹配，正常决策表达不再误报 |
| 危机文本可能进入后续 AI 历史 | 安全内容污染普通回复 | 危机输入和安全回复均从模型历史中排除 |
| 提示词注入测试把拒绝语句误判为泄露 | 回归结果失真 | 只检测密钥形态、肯定性保证和是否回到决策上下文 |
| 对话可能把自拟数字写成事实 | 用户误解阈值来源 | `dialogue.v6` 强制标注建议阈值或待确认假设，并增加真实模型回归 |
| 对话语气测试只找固定口头禅 | 不能判断是否复用当前用户语言 | 改为检查回复是否包含当前 Self Skill 中经原文验证的标志性短语 |
| 最终卡片回退到通用建议 | 个性化体验中断 | 报告与分享页共同使用 `buildDecisionBrief()` |

## 8. 剩余风险

### P0：公开测试前必须持续监控

1. **模型成本和滥用。** 需要按匿名会话记录调用次数、token、延迟和失败原因，并设置日预算与熔断。
2. **提供商故障。** 当前有本地降级；还需要运维告警、失败率阈值和恢复演练。
3. **提示词注入。** 用户日记和聊天内容属于不可信输入，需要持续维护注入测试集并确保模型输出只能通过结构化 schema。
4. **隐私说明。** 微信 AI 分析必须继续保持二次确认，部署方还需在隐私政策中列出模型提供商和保留策略。
5. **高风险建议。** 法律、医疗、财务和人身安全内容需要更完整的分类器与地区化求助资源。

### P1：体验优化

1. 将完整分析拆为两阶段：6 秒内先返回核心画像，其余阶段语气和方案异步补齐。
2. 对 DeepSeek 和 OpenAI 建立相同数据集上的盲评，比较相关性、具体性、语气、延迟和成本。
3. 使用用户留出的真实文本评估语气相似度，替代单纯的材料覆盖分。
4. 用户展开深层节点时按需请求 AI，避免首次生成整棵树和大量 token。
5. 为大型微信记录增加分块摘要、重复内容合并、增量更新和删除审计。

### P2：核心壁垒建设

1. 建立经过用户确认的长期 Self Skill 版本历史。
2. 将“模型判断 -> 用户修正 -> 行为实验 -> 结果反馈”做成训练和评估闭环。
3. 建立人生阶段语气的时间标注语料和长期一致性指标。
4. 为不同模型维护统一的离线评估集、线上 A/B 和回归阈值。

## 9. 发布门槛

### 9.1 每次合并必须通过

```bash
npm run check
npm run build
npm run qa:ai:providers
```

### 9.2 修改 AI 提示词、schema、网关或路由时必须通过

```bash
npm run qa:ai -- --require-live-ai
```

验收要求：

- 关键失败为 0。
- 两个人格场景保持差异。
- evidence 引用完整。
- 危机输入不调用模型。
- 微信 PII 不出现在模型返回。
- AI 或本地降级来源可见。
- 对话回复不超过产品长度上限，并至少给出一个可执行动作。

### 9.3 扩大访问量前必须完成

- 服务端指标和告警。
- 每用户及全局 token 预算。
- 提供商故障演练。
- 隐私政策和数据处理清单。
- 至少 50 个匿名化场景的人工盲评。
- 移动端和低速网络体验验收。

| 指标 | 建议告警阈值 |

## 13. 最终判断

LifeFork 已经拥有可验证的 AI 核心。当前最有竞争力的组合是：个人证据关联、阶段语气、顶层方案生成、可见来源和持续校准。

下一阶段的首要工作是降低首次生成延迟、建立长期语气评估、让深层分支按需个性化，并用真实用户盲评持续判断“它是否理解我”。只有模型调用成功远远不够；核心指标应当落在相关性、可核对性、可执行性和用户修正后的持续改善上。
